让 AI 跑测试之后，谁来判断它真的通过了？

沿着 Verification Layer 继续探索：用 Artemis 执行，用 Jev 辅助判断。

最近，我还在持续思考 Agentic Coding 里的 Verification Layer：AI 写完代码后，我们究竟凭什么相信它完成了需求？

上一篇聊到，用 Maestro 这类工具，可以把测试执行变得更可控。但高质量测试的编写和维护，依然需要投入不少精力。

这让我想继续探索一个方向：能不能让 AI 更灵活地操作 App，同时把“是否满足需求”的判断，单独做成一个可检查的环节？

我最近关注到的两个项目，恰好可以放到这条链路里讨论：Artemis 和 Jev。

我的设想是：Artemis 负责操作和取证，Jev 根据验收标准对证据做分类、给出置信度，再由明确的规则形成测试结论。

这还是一个待验证的方向。下面讨论的是它为什么值得尝试，以及怎样判断它是否真的有用。

跑完流程，只回答了一半问题

假设我们要测试“取消订单”。

自动化工具打开订单页，点击取消，再点击确认，屏幕上出现“取消成功”。整个过程很顺利。

但订单真的被取消了吗？页面状态更新了吗？如果服务端拒绝了请求，App 会不会依然显示成功？

这里其实有两个不同的问题：

  • 执行问题：有没有按要求完成操作？
  • 验收问题：操作后的实际结果，有没有满足需求？

测试自动化需要把这两件事都做好。尤其当执行者本身也是 AI 时，它说“任务完成了”，还需要对应的证据来支持。

Artemis 操作 App，Jev 判断具体问题

Artemis 是 Google 开源的 Android 自动化项目，可以根据自然语言指令操作真机或模拟器，也提供截图、界面结构、执行轨迹和日志等观察能力。这个方向的初步验证，可以先从 Android 场景开始。项目说明 · 取证接口

在这套设想中，它承担执行和取证工作：进入页面、点击按钮、输入内容，记录过程中发生了什么。

Jev 则是 TypeSafe 推出的决策模型。它支持针对输入状态回答预先定义的问题，例如从几个类别中选择一个，并返回概率分布和置信度。官方介绍

因此，我们可以尝试把验收标准拆成小问题，让它逐项判断。例如：

  • 当前页面是否明确表达了“订单已取消”？
  • 错误提示是否告诉用户取消没有成功？
  • 现有证据是否不足以判断这一项？

这种拆分也符合 Jev 官方文档的建议：让模型回答范围明确的问题，再在代码里组合结果。使用说明

如果需要判断订单状态是否等于 cancelled，直接用程序比较就可以。Jev 更值得尝试的地方，是那些需要理解文字含义、又不容易用固定字符串写死的判断。

两者之间，还需要一层“证据整理”

把两个工具接起来，还需要解决一个问题：Jev 到底根据什么作判断？

Jev 当前只接受文本形式的输入，可以用结构化数据组织，但不支持图片和视频。因此，这个方案不能直接假设“把截图丢给 Jev，它就能判断”。输入说明

我们需要先把取到的信息，整理成一份可以核对的证据记录：执行了哪些步骤、页面出现了什么文字、状态在什么时候发生变化。每条记录都应能追溯到原始截图、日志或其他数据。

能直接从界面结构和日志中读取的信息，优先直接读取；必须依赖截图识别的内容，则需要额外的识别环节，而且这个环节也可能出错。

如果验收涉及服务端状态，还需要接入测试接口或业务日志。这部分需要额外建设，不能指望 UI 自动化工具天然知道后台发生了什么。

这样，整个流程可以写成：

明确验收标准 → Artemis 执行 → 整理证据 → 程序断言与 Jev 逐项判断 → 规则汇总 → 反馈给 Coding Agent

验收标准要在执行前确定。交给判断环节的材料，也应保留实际观察，不能只剩执行者的一句“我认为成功了”。

用“取消订单”走一遍

假设这条用例的验收标准已经明确：用户确认取消后，页面显示“已取消”，且服务端的对应订单状态也变成“已取消”。

Artemis 完成操作，采集页面上的文字；测试系统通过额外接入的接口读取订单状态。

这时，可以把“页面是否清楚表达了取消成功”交给 Jev 判断，把“服务端状态是否符合预期”交给程序检查。

如果页面显示成功，但服务端状态仍然是“处理中”，这条用例就不能通过。界面上的成功提示，无法抵消业务状态上的失败。

如果没有拿到服务端证据，这一项就应标记为“证据不足”，等待补充。设备断连、操作没有完成，也要单独记录为执行受阻，不能直接当成产品缺陷。

因此，最终结论至少应该允许三种情况：通过、失败、无法判断。

“无法判断”能让系统知道下一步该补证据、重新执行，还是交给人处理。

置信度的价值，是帮助决定下一步

在这个方案里，置信度可以帮助系统分流：哪些判断可以自动采纳，哪些需要进一步检查。

但这里有个容易混淆的地方：Jev 的 confidence 是根据输出概率分布计算的指标，并不等于“这个测试通过的概率”。高置信度也可能对应一个明确的失败判断。置信度说明

即便模型很有把握，也可能看错。输出符合预定格式，同样不代表业务判断一定正确。

所以，自动通过需要同时满足几个条件：必要证据齐全、明确的程序检查通过，以及需要语义判断的项目达到经过验证的可信程度。关键失败项不能靠其他项目的高分平均掉。

具体阈值要拿自己的测试数据验证。我们尤其需要观察：那些被高置信度判为通过的案例里，到底藏着多少真实缺陷。

先验证它能否抓住已知的错

我会从少量、边界清楚的 Android 用例开始，同时准备正常版本和故意带有缺陷的版本。

例如：成功提示出现但状态没有更新、请求失败后仍然提示成功，或者关键证据缺失。然后把系统结论与人工核对过的结果进行比较。

需要关注的指标也很直接：漏掉了多少缺陷、误报了多少正常结果、有多少情况需要人工介入，以及重复执行时是否稳定。

如果测试中文 App，还要专门检验中文界面的判断效果。Jev 官方文档目前提示，中文等语言的准确率低于英语。语言限制

还要和现有方案比较总成本：少写一些脚本，是否真的省下了时间，还是把成本转移到了证据整理和误判处理上？

只有这些结果站得住，才有理由逐步扩大范围。Artemis 的执行能力和 Jev 的决策能力，都需要放到自己的业务里重新验证。

我期待这套组合带来的，是一条更清晰的反馈链：哪条验收标准没有满足，证据在哪里，接下来该修代码、补证据，还是检查测试环境。

当这些反馈能够稳定地回到 Coding Agent，自动修复才更有可能沿着正确的方向推进。

这也是我继续探索 Verification Layer 的原因：让“代码写好了”之后的每一步，都有足够清楚的依据。
