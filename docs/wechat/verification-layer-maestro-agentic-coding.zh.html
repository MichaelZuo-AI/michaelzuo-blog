Verification Layer 才是 Agentic Coding 的操作系统

从 LLM 生成测试失败，到用 Maestro 构建可复现的需求验证层。

这段时间做 agentic coding pipeline，我越来越明显地感觉到：最难的部分已经不只是“让 Agent 写代码”。

从需求生成 PR，做 multi-sampling、self-evolve、scoring loop，这些都已经能跑起来。真正耗人的，是后面那句更朴素的问题：这个 PR 到底对不对？

一个 Agent 可以很快写出十个候选实现。问题是：哪一个真的满足需求？哪一个只是看起来合理？哪一个没有破坏边界条件？哪一个在明天、下周、另一个设备、另一份测试数据上还能稳定通过？

如果 verification 的成本太高，Agentic Coding 的 ROI 很容易被吃掉。代码是省下来了，但成本转移到了写测试、调 flaky、补 fixture、人工 review、排查 false pass 上。

所以这篇想讨论的不是“怎么让 LLM 多写测试”，而是怎么把 verification 做成一层稳定、可复用、真的能证明需求满足的系统。

Verification Layer 不是让 AI 多写几段测试脚本，而是把需求编译成稳定、可复现、能被评分的 verifier。

瓶颈开始转向验证

LLM 生成代码的 output range 很宽。它可以写出正确实现，也可以写出语法正确、叙述漂亮、但业务上错一半的实现。

Regression testing 相对容易，因为已有行为和已有测试可以复用。New feature testing 难得多，因为需求本身还没有可执行 verifier。

贵的地方也不只是写一段测试脚本，而是把需求拆成可验证条件，准备稳定 fixture，定义 selector，控制环境状态，设计 oracle，执行多轮稳定性检查，再把失败结果映射回具体 acceptance criteria。

如果这些都靠人临时手写，Agentic Coding 只是把开发瓶颈换了一个位置。

第一次尝试：让 LLM 直接写测试脚本

最自然的方案是这样的：

自然语言 test case
→ LLM 生成 test script
→ 执行 test script
→ 用执行结果验证 Agent 生成的 PR

这个方案一开始看起来很合理，因为 LLM 很擅长把自然语言翻译成代码。但真实工程里，它通常会同时暴露两个问题。

第一，测试几乎抓不到 bug

问题不是 LLM 不会写语法，而是它很容易生成“看起来像测试”的脚本，却缺少真正有效的 oracle。

比如需求是“用户可以取消符合条件的订单”。LLM 可能生成一条 flow：打开订单详情页，点击取消按钮，看到成功提示。

但这不够。它可能没有验证非可取消订单是否隐藏按钮，没有验证 confirm modal 是否真的出现，没有验证 confirm 后是否调用正确 orderId，没有验证 API failure 是否保留原状态，也没有验证 loading 期间是否禁止重复提交。

测试能跑，不代表它能证明需求被满足。很多自动生成测试只是 demo flow，不是 verifier。

测试的核心不是 action，而是 oracle。 LLM 生成测试失败，通常不是 action 写错，而是 oracle 太弱。

第二，每次执行结果不稳定

LLM 直接写脚本，还会带来另一类问题：selector 不稳定、timing 不稳定、test data 不稳定、app state 不稳定、执行语义不稳定。

同一条需求，今天用 text selector，明天用 index，后天用 XPath。今天 sleep 两秒能过，明天网络慢一点就失败。今天测试数据还在，明天状态被上次运行污染。

这本质上是在用一个随机系统约束另一个随机系统。结果不是稳定验证，而是把不确定性从 coding agent 转移到了 testing agent。

切到 Maestro 后，稳定性变好了

后来我们切到 Maestro，把测试限制在 YAML-based DSL 里。这个方向是对的。

Maestro Flow 用声明式 YAML 描述用户旅程，比如 launch app、tap、input、assert visible。它把自由代码收敛成统一执行语义，也让测试变得可读、可 review、可版本化。

appId: com.example.app
name: Cancel Order Success Flow
tags:
  - smoke
  - order
---
- launchApp
- tapOn: "Orders"
- tapOn: "Order #123"
- assertVisible: "Cancel Order"
- tapOn: "Cancel Order"
- assertVisible: "Are you sure?"
- tapOn: "Confirm"
- assertVisible: "Order cancelled"

Maestro 的价值很明确：脚本自由度降低，执行引擎统一，YAML 能被 QA、研发、AI 一起维护，也更适合按 feature、tags、common flows 组织测试套件。

但 Maestro 只解决了 reproducibility，没有自动解决 authoring cost。

Maestro 让测试可复现，但不保证测试有价值。测试有没有价值，取决于上层的需求拆解、数据契约和 oracle 设计。

正确方向：Verification Layer as Compiler

所以我现在更倾向于把 verification layer 设计成一个 compiler system，而不是继续让 AI 直接写更多 YAML。

Requirement
→ Acceptance Criteria
→ Goal Tree
→ Verifier Plan
→ Test Intent IR
→ Selector / Data / Oracle Contracts
→ Maestro YAML Compiler
→ Static Validation
→ Multi-run Stability Check
→ Mutation / Bug-catching Check
→ AC Coverage Scoreboard

旧范式是：自然语言 test case 进 LLM，直接吐出可执行脚本。

新范式是：LLM 先生成结构化 verification intent，再由确定性 compiler 生成 Maestro YAML。

这更像编译器。自然语言需求是 source language，Test Intent IR 是 intermediate representation，Maestro YAML 是 target bytecode，Maestro runtime 是 execution engine，coverage scoreboard 是 verification output。

LLM 负责它擅长的部分：理解需求、拆解场景、选择验证策略、补全边界条件。确定性系统负责它擅长的部分：模板化、编译、静态检查、执行、复现和评分。

Test Intent IR：不要直接生成 YAML

IR 的目标，是把“测试意图”从“低层点击步骤”里抽出来。

feature_id: order_cancel
flow_id: order_cancel_success
intent: eligible user cancels an order successfully
source_acceptance_criteria:
  - AC1: Only cancellable orders show cancel button
  - AC2: Clicking cancel opens confirmation modal
  - AC3: Confirming calls cancel order API
  - AC4: Success refreshes order status
scenario_type: positive
preconditions:
  user: user_with_cancel_permission
  order: order_eligible_cancel_001
oracles:
  - success toast visible
  - cancel button not visible
  - order status becomes CANCELLED
engine: maestro
priority: pr_smoke

Human review IR 的成本，远低于 review 一长串低层 YAML。IR 更贴近需求语义，也方便 coverage system 追踪每条 AC 是否有 verifier。

Compiler 再根据 IR、selector registry、fixture registry 和 flow templates 生成 Maestro YAML。

关键是：LLM 可以参与生成 AC、Goal Tree、oracle 建议和失败解释，但低层 YAML 应尽量由模板和 registry 确定性生成。

四类 Contract 决定稳定性

LLM 直接生成脚本不稳定，背后通常是缺少四类 contract。

Selector Contract

测试需要稳定找到 UI 元素。不应该让 LLM 每次猜“Cancel”“取消订单”“第三个按钮”或 XPath。产品代码和测试系统应该共同定义稳定 selector，比如 order.cancel.button、order.cancel.confirm_modal、order.cancel.error_toast。

Data Contract

测试必须知道初始状态是什么。比如 order_eligible_cancel_001、order_shipped_001、order_cancel_api_fail_001。LLM 只选择 fixture，不临时编造数据。

Environment Contract

登录态、权限、实验开关、系统时间、locale、网络和 app state 都要被控制。否则 flow 失败时，你很难判断是功能 bug、测试 bug、数据污染还是环境问题。

Oracle Contract

每条测试必须明确什么算对。比如取消订单成功，不只看 toast，还要看状态变成 cancelled、按钮消失、错误路径保持原状态、重复点击不会发多次请求。

让测试真的能抓 bug

一个 verification suite 的价值，不是它通过了多少测试，而是它能杀掉多少典型 bug。

这就是 mutation testing 在这里的意义。我们可以为每类 feature 建一个 Bug Seed Library，然后检查测试是否能发现这些已知错误。

Bug Seed 1: 所有订单都显示 Cancel button
Bug Seed 2: confirm 后没有调用 API
Bug Seed 3: API 调用 orderId 错误
Bug Seed 4: success 后没有刷新订单状态
Bug Seed 5: failure 时仍显示 success toast
Bug Seed 6: loading 状态下可以重复提交

如果 Maestro flow 在这些 bug 存在时仍然全部通过，说明它不是 verifier，只是 demo script。

Bug-catching score 可以定义成 killed mutations / total seeded mutations。它比单纯 test pass 更有价值，因为 test pass 只能说明当前代码没触发测试失败，mutation killed rate 才能说明测试有没有能力发现错误。

AC Coverage Scoreboard

每个 PR 最后不该只输出 tests passed，还应该输出 requirement-level 的 scoreboard。

feature_id: order_cancel
overall_requirement_score: 0.78
AC1_only_cancellable_orders_show_cancel: covered_passed
AC2_clicking_cancel_opens_modal: covered_passed
AC3_confirm_calls_api: covered_failed
AC4_success_refreshes_status: covered_failed
AC5_failure_shows_error: missing_verifier
stability: pass_rate 0.8
bug_catching: 4 / 6

评分也需要分层：build、typecheck、lint、critical regression、YAML static validation 是 hard gate；AC coverage、subgoal pass rate、mutation score 是 requirement score；diff size、pattern reuse、maintainability、flake rate 是 quality score。

Quality score 不能覆盖 requirement score。一个 diff 很小但漏掉关键 AC 的 PR，不应该比一个完整满足 AC 但稍微复杂的 PR 得分更高。

把 flakiness 当成一等公民

每个新 flow 生成后，不要只跑一次。至少要做 multi-run stability check。

PR smoke: failed flow rerun 2 次
Nightly validation: newly generated flows rerun 5 次
Release gate: critical flows rerun 10 次

如果 5 次里有 2 次失败，它就不能直接进入 PR gate。系统应该先 triage：selector instability、timing issue、test data pollution、app state leakage、environment issue、real product bug，还是 Maestro YAML bug。

不同分类对应不同修复策略。Selector 不稳，就补 testID 或 accessibility id；timing 问题，就用状态断言替代 sleep；数据污染，就在 flow 前 seed 和 reset；真实产品 bug，才反馈给 coding agent 修业务代码。

降低 Maestro YAML 编写成本

这里的目标不是让 AI 每次从零写 YAML，而是把验证资产沉淀成可复用系统。

Flow Component Library：把 reset_app、login、logout、open_deeplink、seed_order、grant_permissions、set_locale、wait_for_home 变成 common flows。Feature flow 只负责业务场景。

Selector Registry：让 compiler 从 registry 生成 Maestro selector。如果 registry 找不到 selector，不让 LLM 猜，而是生成一个 implementation requirement：请在 production code 中为目标元素增加稳定 test surface。

Data Fixture Registry：把 order_eligible_cancel_001、user_without_cancel_permission_001 这类数据纳入 registry。LLM 选择 fixture，seed API 创建状态，测试不再依赖偶然数据。

Flow Templates by Feature Type：给 api_mutation、permission_logic、form_change、error_handling 这类高频 feature 建模板。LLM 填 slot，compiler 渲染 YAML。

Human 不应该长期手写每条测试脚本，而应该维护 selector、fixture、template 和 oracle policy。人的工作从“写脚本”升级为“维护验证系统”。

BES 和动态规划的启发

BES 给我的启发是：不要只用最终结果作为稀疏 reward，而要把目标拆成可验证子目标，再用 dense feedback 指导搜索。

Agentic Coding 里也一样。不要只问“这个 PR 是否实现了取消订单”，而是拆成入口展示、确认交互、API 行为、success 状态、failure 状态、权限边界、重复提交等 leaf goals。每个 leaf goal 都对应一个 verifier。

如果 mutation testing 发现 success 后不刷新状态的 bug 没有被 kill，系统就应该把“success refreshes order status”继续拆成 API response、query refetch、UI status update、cancel button disappears，再生成更细的 oracle。

动态规划给 verification layer 的启发则更直接：不要重复解决同一个子问题。

登录、deeplink、seed 数据、等待 loading、验证 toast、验证 permission denied、验证 confirm modal，这些都可以缓存成已验证的 subflow、template 或 oracle。新 feature 的 verification 就不必从零开始。

推荐落地路线

  1. 先把 Maestro YAML 的手写成本结构化：selector、data、flow、assertion、flake、review 分别贵在哪里。
  2. 建立 Test Intent IR，让 AI 先生成可 review 的测试意图，而不是直接写 YAML。
  3. 建立 Selector Registry 和 Fixture Registry，这是稳定性的基础。
  4. 先支持 3 到 5 个高频 feature template，比如 UI entry point、API mutation、form change、permission logic、error handling。
  5. 做 IR 到 Maestro YAML 的 template-based compiler，不必一开始追求复杂。
  6. 加入 Stability Gate，让新 flow 多次运行后再进入 PR gate。
  7. 加入 Mutation / Bug-catching Check，验证测试是否真能抓典型 bug。
  8. 最后接入 Agentic Coding PR Loop，让失败结果映射回 AC 和 subgoal，指导 coding agent 修复。

应该看哪些指标

判断 verification layer 是否有效，不应该只看“测试数量”。更有用的是这些指标：

  • AC-to-verifier coverage rate：每条 acceptance criterion 是否有 verifier。
  • Bug-catching score：seeded bugs 被测试抓出的比例。
  • Flake rate：多次运行中不稳定失败的比例。
  • YAML authoring cost：每条 flow 从需求到稳定运行需要多少人时。
  • YAML reuse rate：新 flow 中多少步骤来自 common flow 或 template。
  • False pass rate：PR 通过 verification，但 human review 发现需求未满足的比例。
  • Cost per verified PR：生成、验证、修复、review 的总成本。

其中最重要的是 false pass rate、bug-catching score、YAML authoring cost 和 flake rate。它们直接决定这个系统是降低成本，还是制造一层新的复杂度。

最终架构

Feature Requirement
→ Goal Tree / AC
→ Test Intent IR
→ Selector + Fixture + Oracle Contracts
→ Maestro YAML Compiler
→ Execution + Stability + Mutation
→ AC Coverage Scoreboard
→ Agentic Coding Repair Loop

这套系统要解决的，不是“怎么让 AI 多写几条测试”。它要解决的是：如何低成本、稳定、可复用地把需求变成可执行 verifier。

没有 verification layer，LLM 的随机性是风险。有了 verification layer，LLM 的随机性才会变成搜索能力。

这也是为什么我认为 Verification Layer 更像 Agentic Coding 的操作系统。它决定代码生成是否有反馈，反馈是否可复现，失败是否能定位，修复是否能收敛，最终 PR 是否真的满足需求。
