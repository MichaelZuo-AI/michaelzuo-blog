Verification Layer 才是 Agentic Coding 的最后一公里

构建确定性的系统去约束不确定性。

过去一段时间，Agentic Coding 经历了一个很典型的认知周期。

最开始，大家对它的期待很简单：既然 LLM 已经可以理解需求、写代码、改代码，那人是不是终于可以从 coding 里解放出来？只要把 intent 交给 AI，它就能自动生成 feature code，甚至自动提交 PR。

这个想法很有吸引力，也确实在很多 demo 里展示出了惊人的效果。但真正落地之后，很多团队会经历从“膜拜”到“怀疑”的过程。

Demo 可以很惊艳。但要持续稳定地生成符合业务预期、工程规范、系统设计和质量要求的代码，远比想象中困难。

我不认为这说明 Agentic Coding 走错了方向。相反，这说明它正在进入真正的工程化阶段。

LLM 已经提供了可能性。下一块拼图，不是再让模型多写几行代码，而是建立足够强的 harness engineering。这里面最核心的一层，就是 Verification Layer。

Agentic Coding 的最后一公里，不是 code generation，而是 verification。

为什么 Verification 是核心

在真实软件开发中，无论是人还是 AI，都不能天然保证写出来的代码一定符合 feature requirement。

原因很简单：需求本身经常不完备，甚至可能和现有系统冲突。

一个典型场景是，产品需求说要在原有功能上新增一个能力，但需求文档里对原有功能的描述本身就是错的。人类工程师在开发时，会基于系统背景、历史上下文、团队沟通、产品确认、QA 反馈，不断修正自己对 requirement 的理解。

AI 很难自动完成这一整套隐性沟通。它能读文档、读代码、读上下文，但它无法天然知道哪些需求描述是错的，哪些旧逻辑不能改，哪些边界条件是团队默认约定，哪些异常路径虽然没写进需求但必须支持。

所以对 Agentic Coding 来说，更现实的方向不是期待 AI 第一次就写对，而是建立一套机制：

无论 AI 怎么生成 code，Verification Layer 都能告诉它：

1. 哪里不符合预期？
2. 预期应该是什么？
3. 对应哪条 requirement / acceptance criterion？
4. 应该修 production code、test code、fixture，还是 requirement 本身需要澄清？

这和人类开发其实很像。

人写代码也会出 bug。QA 提 bug，人分析 root cause，再调整代码修复。区别在于：如果我们希望 AI 可以持续 self-looping，那么 QA 的能力必须变成机器可执行、可复现、可评分的 Verification Layer。

没有这个层，Agentic Coding 就只能停留在“生成代码看起来不错”的阶段。有了这个层，Agentic Coding 才能进入“持续修正直到满足需求”的阶段。

当前 Pipeline 的真正瓶颈

很多团队现在已经能搭出这样的 pipeline：

Intent
→ Spec
→ Plan
→ Code Generation
→ Test / Build
→ Repair Loop
→ PR

更进一步的，也已经在做 multi-sampling + self-evolve + scoring：

生成多个 PR candidates
→ 执行验证
→ 给每个 candidate 打分
→ 选择高分 candidate
→ 让 Agent 继续修复或演化
→ 最终提交分数达标的 PR

这个方向是对的。因为 LLM 的输出具有随机性，单次 generation 不稳定，多 sampling 和 self-evolve 可以提高搜索到好结果的概率。

但实际落地后，会遇到两个非常关键的问题。

第一，Looping 得出 best score 的时间太长

如果 verification signal 很稀疏，Agent 并不知道具体哪里错了，只知道：

test failed
build failed
score not enough

于是它只能反复 retry 或大范围 rewrite。每一轮都要重新生成 patch、跑测试、读日志、修复、再跑。随着 feature 复杂度上升，looping 成本会迅速膨胀。

最后你会发现，自动化生成 PR 的成本并不只是 LLM token cost，还包括代码生成、多轮修复、测试生成、测试执行、flaky debug、human review、requirement clarification 等一整串成本。

当这些都算进去，有些 feature 甚至还不如人直接开发。

第二，Best score 不等于满足 requirement

这个问题更致命。

即使得到了 best score，也不代表这个 PR 真正满足 feature requirement。因为很多 scoring 体系偏向工程检查：

lint pass
typecheck pass
build pass
regression pass
unit test pass
diff size reasonable

这些都很重要，但它们无法充分证明新功能真的符合需求。

比如一个“取消订单”的功能，PR 可能所有 existing regression 都过了，但仍然漏掉：

非可取消订单不应该展示取消按钮
点击取消后必须出现确认弹窗
confirm 后必须调用正确 orderId
API failure 后必须显示错误 toast
success 后必须刷新订单状态
loading 时必须禁止重复提交

这说明我们优化的是 verification score，但这个 score 和真实 requirement satisfaction 没有完全对齐。

所以 Agentic Coding 的核心挑战不是“怎么生成更多 PR”，而是如何高效建立一个能真正 verify requirement 的 Verification Layer。

我们踩过的坑：让 LLM 直接写测试脚本

我们曾经做过一个很自然的尝试：

自然语言 test case 描述
→ LLM 生成 test script
→ 执行 test script
→ 用执行结果验证 Agent 生成的 PR

这个方案看起来非常合理。LLM 擅长把自然语言转换成代码，测试脚本本质上也是代码，那么为什么不直接让 LLM 写测试？

但实际效果并不好，主要表现为两个问题。

第一，几乎无法测试出 bug

LLM 生成的脚本经常可以跑，但很难抓 bug。

原因不是它不会写语法，而是它常常生成的是“看起来像测试”的脚本，而不是一个真正的 verifier。

典型问题包括：只覆盖 happy path，不覆盖 negative / edge / permission case；断言太弱，只验证页面出现了，不验证业务状态真的变化；没有把 acceptance criteria 拆成可验证条件；没有验证 API 是否被调用、参数是否正确；没有验证状态刷新、错误处理、重复提交等关键路径。

比如需求是：

用户可以取消符合条件的订单

LLM 可能生成这样的脚本：

打开订单详情页
点击取消按钮
点击确认
看到成功提示

这个脚本看起来合理，但它没有验证：非可取消订单是否隐藏按钮，确认弹窗是否真的出现，confirm 后是否调用正确 API，API 失败时是否显示错误 toast，成功后订单状态是否刷新，重复点击是否被禁用。

因此它能跑通，但不能证明需求被满足。

LLM 直接生成 test script 时，最容易生成的是“可运行脚本”，不是“可证明需求被满足的 verifier”。

第二，每次执行结果都不稳定

同一个自然语言 test case，不同 LLM 采样可能生成不同脚本；同一个脚本，不同时间跑结果也可能不同。

不稳定通常来自这些地方：selector 不稳定，timing 不稳定，test data 不稳定，app state 不稳定，assertion 不稳定，execution semantics 不稳定。

最后结果是：每一轮测试的结果都不一样，同样的 case 有时候过，有时候失败，有时候根本没有测到真正的问题。A candidate 失败，B candidate 过，但无法判断是 code bug 还是 test bug。修复一次测试，下一次又引入新的 flaky。

本质上，这是在用一个随机系统去约束另一个随机系统。

LLM-generated code 是随机的；
LLM-generated test script 也是随机的。

两个随机系统叠加，不会产生稳定验证，只会把不确定性从 coding agent 转移到 testing agent。

切换到 Maestro：稳定性提升了，但成本转移了

后来我们做了一个尝试：切换到 Maestro 作为测试引擎，采用 AI + 人工生成 YAML，也就是 Maestro 的 test script。AI 只辅助生成 YAML，但后续自动化测试执行全部由程序完成。

这个方案带来了明显提升。

Maestro 的 Flow 是 YAML-based test scripts，用来定义 UI automation 的 user journey。它通过声明式 commands 模拟用户行为和验证 UI 状态，比如 launchApp、tapOn、inputText、assertVisible。

这种 DSL 的价值在于：

测试脚本从自由代码变成声明式 YAML
执行语义由 Maestro runtime 统一控制
YAML 可读、可 review、可版本化
selector、wait、assertion 有更稳定的规范
QA、研发、AI 可以共同参与维护

相比让 LLM 直接生成任意 test script，Maestro 把测试表达限制在一个更小、更稳定、更可控的空间里。

这解决了 reproducibility 的一大部分问题。

但新的问题也很明显：

Maestro YAML 的质量稳定了，但编写和维护 YAML 的成本太高。

写一个高质量 Flow 并不是把自然语言翻译成点击步骤。它还需要处理测试前如何 seed 数据，用哪个账号和环境，页面如何稳定进入，哪些 selector 最稳定，哪些 assertion 才能证明需求满足，如何覆盖 success / failure / permission / edge case，如何拆 common flow，以及 PR 阶段和 nightly 阶段分别跑哪些 flows。

所以 Maestro 解决了稳定执行的问题，但没有自动解决 verification authoring cost。下一步真正要解决的是：如何低成本生成高质量 Maestro YAML，并保证它真的 verify requirement。

下一步：从脚本生成走向验证系统

如果继续往下展开，这会变成一个更完整的未来架构：Requirement Normalizer、Goal Tree Builder、Verifier Planner、Test Intent IR、Selector / Data / Oracle Contracts、Maestro YAML Compiler、Static Validator、Stability Gate、Mutation Check、AC Coverage Scoreboard 和 Failure Triage。

这一整套东西值得单独写一篇文章。这里先埋一个引子，不在这篇里全部展开。

核心转变是：不要让 LLM 直接生成最终测试脚本，而是让它生成结构化的 Verification Intent。然后由确定性的 compiler、registry 和 validator，把这个 intent 编译成稳定 Maestro YAML，并把执行结果映射回 acceptance criteria。

这个方向里有几个关键点：

  • 把需求拆成可验证子目标，而不是只给一个最终分。
  • 把测试意图和测试脚本解耦，用 IR 承载 AC mapping、fixture、selector 和 oracle。
  • 用 compiler 生成 Maestro YAML，减少 LLM 自由发挥带来的不稳定。
  • 用 selector、data、oracle contracts 降低 flakiness。
  • 用 AC Coverage Scoreboard 和 Mutation Check 判断测试是不是真的能证明需求满足。

后面我会单独写一篇，把这一层 Verification Layer 的架构、IR 设计、compiler 设计、scoreboard 和 failure triage 展开讲。

结论：Verification Layer 是 Agentic Coding 的操作系统

Agentic Coding 之所以让人失望，并不是因为 LLM 不会写代码。

真正的问题是：LLM 的输出空间太宽，随机性太强；需求本身不总是清晰和一致；现有验证信号太稀疏；测试脚本生成不稳定；高质量 YAML verifier 编写成本太高；最终 score 和真实 requirement satisfaction 没有完全对齐。

所以未来的方向不是单纯追求更强的 code generation，而是构建一个更强的 verification system。

这个系统要做到：

把需求拆成可验证子目标
把测试意图和测试脚本解耦
用 IR + Compiler 生成稳定 Maestro YAML
用 selector / data / oracle contracts 降低不确定性
用 static validation 和 stability gate 保证复现
用 mutation check 证明测试能抓 bug
用 AC Coverage Scoreboard 让分数对齐需求
用 failure triage 指导 Agent 精准修复

一句话总结：

Agentic Coding 的下一阶段，不是让 AI 更自由地写代码，而是让 AI 在一个完整、可依赖、可持续演进的 Verification Layer 约束下写代码。

代码生成是执行层。

Verification Layer 才是控制层。

当 Verification Layer 足够完整、稳定、低成本，LLM 的随机性就不再只是风险，而会变成可搜索、可筛选、可演化的生产力。

这才是 Agentic Coding 真正走向工程化的关键。
