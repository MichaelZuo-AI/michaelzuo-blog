Verification Layer 才是 Agentic Coding 的操作系统

从 LLM 生成测试失败，到用 Maestro 构建可复现的需求验证层。

过去一段时间，我在想 agentic coding 的时候，越来越少讨论“模型能不能写代码”。

它当然能写。

真正麻烦的是另一件事：它写完以后，我们怎么知道它真的做对了。

这件事听起来像测试工程。但在 agentic coding 里，它其实更像操作系统。Agent 可以生成 diff，可以反复 sampling，可以 self-evolve，可以拿 score 继续搜索。但如果底下没有一个稳定的 verification layer，这些动作很容易变成更快地生产不确定性。

代码不是最稀缺的东西。可信的验证才是。

我现在更愿意把 agentic coding 看成一个搜索系统。模型负责提出候选答案，verification layer 负责告诉它哪里是真的、哪里只是看起来合理。

瓶颈换地方了

以前写功能，瓶颈在实现。需求来了，人理解需求，写代码，写测试，review，上线。

现在有了 coding agent，实现这一步被加速了。一个需求可以生成多个候选 PR。甚至可以让 agent 自己修失败、自己再跑一轮。

但这不会自动带来 ROI。

因为每一个候选 PR 都要被验证。你要知道它有没有满足需求，有没有漏掉 edge case，有没有破坏旧行为，有没有只是把 UI 做到“看起来差不多”。

Regression testing 相对舒服。旧行为已经在那里，测试也常常已经在那里。New feature testing 麻烦得多。需求刚出现的时候，它还没有一个可执行的 verifier。

所以成本不是消失了。它从写代码，移动到了构建验证层。

我一开始也走了最自然的路

最自然的想法是：既然 LLM 会写代码，那就让它根据自然语言 test case 直接写测试脚本。

自然语言 test case
→ LLM 生成 test script
→ 执行 test script
→ 用结果验证 PR

这个方案很有诱惑力。它顺着模型最擅长的能力走：把自然语言变成代码。

但真实跑下来，问题很明显。

它经常能生成可运行脚本，却生成不了足够好的 verifier。

可运行，不等于能抓 bug

测试脚本最容易写出来的是 action。

打开页面。点击按钮。看到 toast。

这些动作很像测试，也确实能跑。但它们不一定能证明需求满足了。

比如需求是“用户可以取消符合条件的订单”。LLM 很可能写出这样的 flow：打开订单详情页，点击取消按钮，看到成功提示。

这条 flow 有用，但太薄了。

它没有问：不可取消订单有没有隐藏按钮？confirm modal 有没有真的出现？confirm 前有没有误调用 API？confirm 后调用的是不是正确 orderId？API 失败时有没有保留原状态？loading 期间能不能重复提交？success 后订单详情有没有刷新？

这些才是 bug 常躲的地方。

测试的核心不是“做了哪些动作”，而是“什么证据能反驳这个实现”。

我后来越来越觉得，很多 LLM 生成的测试不是 verification flow，而是 demo flow。

Demo flow 会证明这个功能在一个顺滑路径里看起来正常。Verifier 要证明它在关键条件下没有撒谎。

这是两件事。

另一个问题是它自己也不稳定

直接让 LLM 写测试脚本，还有一个更工程化的问题：同一个 test case，不同采样会写出不同脚本。

这次用 text selector。下次用 index。再下次用 XPath。今天加 sleep 两秒，明天加 wait。今天假设账号里有订单，明天换一个测试环境就没有了。今天状态是干净的，明天被上一轮测试污染了。

最后失败了，你很难判断它到底是哪种失败。

是产品 bug？测试 bug？数据 bug？环境 bug？还是脚本本身写得太随意？

这就是用一个随机系统去约束另一个随机系统。表面上自动化了，实际只是把不确定性换了个位置。

切到 Maestro 后，事情变好了一部分

后来我们切到 Maestro。这个选择本身是有价值的。

Maestro 把 UI automation 收敛到 YAML DSL 里。你写的是 launchApp、tapOn、inputText、assertVisible 这些声明式命令，而不是一段自由度很高的脚本代码。

appId: com.example.app
name: Cancel Order Success Flow
tags:
  - smoke
  - order
---
- launchApp
- tapOn: "Orders"
- tapOn: "Order #123"
- assertVisible: "Cancel Order"
- tapOn: "Cancel Order"
- assertVisible: "Are you sure?"
- tapOn: "Confirm"
- assertVisible: "Order cancelled"

这件事降低了很多噪音。

YAML 比自由脚本更容易 review。执行引擎统一，行为也更可复现。目录、tags、common flows 这些东西，也让测试套件更容易被组织起来。

但 Maestro 只解决了一半。

它让测试更稳定，却没有自动让测试更有价值。它降低了 runtime 的不确定性，但没有消除 authoring 的成本。

Maestro 不是终点，它更像目标运行时

我不太想把 Maestro 理解成“一个让人手写 YAML 的工具”。

在 agentic coding 里，它更像 verification layer 的 target runtime。

也就是说，最终要执行的是 Maestro YAML。但不代表 YAML 一定要由 LLM 或人从零直接写。

更稳的方式是中间多一层。

Requirement
→ Acceptance Criteria
→ Goal Tree
→ Test Intent IR
→ Selector / Data / Oracle Contracts
→ Maestro YAML Compiler
→ Static Validation
→ Multi-run Stability Check
→ Bug-catching Check
→ AC Coverage Scoreboard

这听起来像架构词，但本质很简单。

我会把 LLM 放在更适合它的位置上：先写测试意图。然后用确定性的模板、registry 和 compiler，把意图翻译成 Maestro YAML。

自然语言需求是 source。Test Intent IR 是中间表示。Maestro YAML 是 bytecode。Maestro 是 runtime。Scoreboard 是验证输出。

IR 的价值是让人 review 意图

我不想让人 review 一大段低层点击步骤。那太容易陷进去，也很容易漏掉真正的问题。

更好的 review 对象是 Test Intent IR。它描述的是这个测试到底想证明什么。

feature_id: order_cancel
flow_id: order_cancel_success
intent: eligible user cancels an order successfully
source_acceptance_criteria:
  - AC1: only cancellable orders show cancel button
  - AC2: clicking cancel opens confirmation modal
  - AC3: confirming calls cancel order API
  - AC4: success refreshes order status
preconditions:
  user: user_with_cancel_permission
  order: order_eligible_cancel_001
oracles:
  - success toast visible
  - cancel button disappears
  - order status becomes CANCELLED
priority: pr_smoke

这份 IR 里最重要的不是步骤，而是三件事：它覆盖哪条 AC，用什么数据跑，用什么 oracle 判断正确。

Human review 也因此变得更有意义。人不用纠结某一步 YAML 缩进怎么写，而是看它有没有漏掉 failure case、有没有弱 oracle、有没有用错 fixture。

低层 YAML 交给 compiler。人看意图。

稳定性来自 contract，不来自祈祷

测试要稳定，光换成 DSL 不够。还要把几个 contract 补上。

Selector Contract：测试系统不能每次猜“取消订单”这个按钮在哪里。产品代码要暴露稳定的 test surface，比如 order.cancel.button、order.cancel.confirm_modal。

Data Contract：测试要知道自己跑在什么初始数据上。order_eligible_cancel_001、order_shipped_001、order_cancel_api_fail_001 这类 fixture 最好被注册和复用，而不是每条 flow 临时编一份。

Environment Contract：登录态、权限、实验开关、系统时间、locale、网络和 app state 都要尽量可控。否则失败结果没有诊断价值。

Oracle Contract：每条测试要说清楚什么算对。只看 toast，通常太弱。要看业务状态、按钮状态、API 行为、错误路径和重复提交这些更硬的证据。

我会用 seeded bug 反过来测测试

判断一个 verification suite 有没有价值，我不会只看它 pass 了多少测试。

我更想看它能不能杀掉典型 bug。

还是取消订单这个例子。可以故意注入几类 bug：

Bug 1: 所有订单都显示 Cancel button
Bug 2: confirm 后没有调用 API
Bug 3: API payload 里的 orderId 错了
Bug 4: success 后页面状态没有刷新
Bug 5: failure 时仍然显示 success toast
Bug 6: loading 时可以重复提交

如果这些 bug 在代码里，测试还全部通过，那它就不是 verifier。

这就是 mutation testing 在这里的价值。它不是为了学术上的测试覆盖率好看，而是为了回答一个很朴素的问题：

这套测试到底能不能抓住我们真的担心的错误？

Scoreboard 也要贴着需求

很多 agentic coding loop 最后会给一个总分。

总分有用，但也危险。一个 diff 很小、风格很好、测试也跑过的 PR，仍然可能漏掉关键 AC。

所以我更喜欢 AC Coverage Scoreboard。它不只说 tests passed，而是说每条验收标准现在是什么状态。

AC1: only cancellable orders show cancel button → covered_passed
AC2: clicking cancel opens modal → covered_passed
AC3: confirm calls API → covered_failed
AC4: success refreshes status → covered_failed
AC5: failure shows error → missing_verifier
stability: pass_rate 0.8
bug_catching: 4 / 6

这样 agent 修复时也更清楚。不是“这个 PR 分数不够”，而是“AC3 没有观察到 API call，AC5 根本没有 verifier”。

反馈越具体，下一轮搜索越有价值。

Flaky 不能留到最后再管

如果 verification layer 自己不稳定，agentic coding 会很快变得不可用。

新 flow 不能只跑一次。PR smoke 可以 rerun failed flow。Nightly 可以对新生成 flows 跑 5 次。Release gate 可以对关键 flows 跑更多次。

重点不是数字，而是把 flakiness 当成系统的一等信号。

失败以后也不要立刻让 coding agent 改业务代码。先分类：selector 不稳、timing 问题、数据污染、app state 泄漏、环境问题、YAML bug，还是真实产品 bug。

不同失败要走不同路径。否则 agent 会很努力地修一个根本不在产品代码里的问题。

降低成本靠复用，不靠每次更聪明

Maestro YAML 的编写成本，我不想靠“让 AI 这次写得更好”来解决。

更可靠的方式是把重复问题沉淀下来。

登录、reset app、open deeplink、seed order、grant permissions、set locale、wait for home，这些可以沉淀成 common flows。

API mutation、permission logic、form validation、error handling，这些可以沉淀成 feature templates。

selector 和 fixture 进 registry。找不到 selector 的时候，输出不该是让 LLM 现场猜，而是告诉产品代码：这里需要补一个稳定 testID。

这会倒逼产品代码暴露更稳定的 test surface。验证层和产品代码才会形成闭环。

BES 给我的启发

BES 里我觉得最有价值的不是某个具体算法，而是一个思路：不要只靠最终结果这个稀疏反馈，要把目标拆成可以验证的子目标。

Agentic coding 也是这样。

与其只问“这个 PR 是否实现了取消订单”，不如拆成入口展示、确认交互、API 行为、success 状态、failure 状态、权限边界、重复提交。

每个 leaf goal 都要有 verifier。哪个 leaf fail 了，agent 就修哪个 leaf。

动态规划的启发也一样直接：不要重复解决同一个子问题。

已经稳定验证过的登录、seed、deeplink、confirm modal、permission denied，没有必要每次重新生成。缓存起来，组合起来。新 feature 的验证成本才会真的下降。

如果从明天开始做

我不会一开始就追求全自动。

第一步，先把现在手写 Maestro YAML 的成本拆清楚：selector 查找贵在哪里，fixture 准备贵在哪里，flow 编排贵在哪里，assertion 设计贵在哪里，flake debug 又浪费在哪里。

第二步，让 AI 先生成 Test Intent IR，不直接生成 YAML。人 review IR，看它有没有覆盖需求和关键风险。

第三步，补 Selector Registry 和 Fixture Registry。这两个东西没起来之前，自动生成测试大概率还是会飘。

第四步，只支持最常见的 3 到 5 类 feature template。比如 UI entry point、API mutation、form change、permission logic、error handling。

第五步，做一个朴素的 IR 到 Maestro YAML compiler。先 template-based rendering 就够了。

然后再加 stability gate、mutation check、AC coverage scoreboard。

最后接回 coding agent 的 repair loop。这个时候 agent 不是在盲修，它是在修一个明确失败的 subgoal。

真正该看的指标

如果要判断这套 verification layer 有没有用，我会优先看四个指标。

第一，false pass rate。PR 通过验证，但 human review 发现需求没满足，这个比例必须往下走。

第二，bug-catching score。Seeded bugs 被杀掉的比例要上去。

第三，YAML authoring cost。从需求到稳定 flow，消耗的人时要下降。

第四，flake rate。验证层自己不能成为主要噪音源。

其他指标也有用，比如 AC coverage、fixture reuse、selector stability、repair targeting accuracy。但上面四个最直接。它们决定这套系统是在降低成本，还是只是把工程复杂度包装得更漂亮。

最后

Agentic Coding 要规模化，不能只依赖更强的模型、更大的 sampling、更多 self-evolve loop。

这些都重要。但如果没有稳定、低成本、需求对齐的 verification layer，模型越强，只是越会生产看起来合理的候选答案。

我们从 LLM 直接生成测试脚本的失败里看到：自由生成测试会带来弱 oracle 和执行不稳定。

我们从 Maestro 的实践里看到：稳定 DSL 能显著提升复现性，但 YAML authoring cost 会成为新的瓶颈。

下一步不是让 AI 更努力地写测试脚本。

下一步是把 verification layer 设计成一个 compiler system：AI 负责需求理解和 test intent，确定性工具负责 IR 到 Maestro YAML 的生成、校验和执行；selector、data、oracle contracts 保证稳定性；AC coverage 和 mutation testing 保证测试真的能抓 bug。

没有 verification layer，LLM 的随机性是风险。有了 verification layer，LLM 的随机性才会变成搜索能力。
