# Artemis + Jev：AI 跑完测试之后，谁来验收？

最近，Google 开源了 [Artemis](https://github.com/google/artemis)，TypeSafe 的 Jev 也一下子热了起来。Vercel 甚至专门发了一篇文章，说 Jev 成了 AI Gateway 历来被采用最快的模型。[Vercel 的发布记录](https://vercel.com/blog/ai-gateway-jev-model-launch)

这两个项目做的事情不太一样，但放在一起看，还挺有意思。

## Artemis：让 AI 真正去操作手机

Artemis 是一个面向 Android 的自动化项目。你可以用自然语言描述任务，让它在真机或模拟器上执行。它会根据当前界面寻找目标，完成点击、输入、滑动这些操作，也能处理跨 App 的流程。[Artemis 项目说明](https://github.com/google/artemis)

比如，可以把“打开 App，登录测试账号，找到某个商品，进入详情页”这样的任务交给它。你描述想做什么，再由它根据实际页面决定怎么操作。

对做 mobile automation 的人来说，这种方式很容易理解：原来需要写进脚本的部分操作过程，现在可以尝试交给 agent 去完成。

它还提供截图、界面结构、执行轨迹和日志等信息，也能通过 MCP 接进 coding agent 的工作流。这样，agent 写完代码以后，就有了一条继续到设备上操作、观察结果的路径。[取证与集成接口](https://github.com/google/artemis/blob/main/mcp_server/README.md)

我比较在意的是，操作过程能留下记录。走到了哪个页面，点了什么，界面怎么变化，出了问题以后，有东西可以回头查。

当然，它目前聚焦 Android。具体能不能把我们的业务流程跑好，还是要拿真实 App 来试。

## Jev：把判断变成程序可以直接使用的结果

Jev 来自 TypeSafe。官方把它归到一类叫 System One 的模型里。这个名字听起来有点抽象，我觉得可以先把它理解成一个能被程序调用的判断器。[Jev 官方介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

你给它一些信息，再定义好要问的问题和可选答案，它就返回对应的结果。

比如，收到一张客服工单，可以让它判断这是退款问题还是技术故障，也可以按事先定义的标准给紧急程度打分。后面的程序拿到结果，就能决定把工单交给哪个团队、要不要优先处理。

这里比较有意思的是，Jev 的分类和评分结果会带上概率分布和置信度。程序除了拿到“选了什么”，还可以利用这些信息，决定是继续执行，还是把拿不准的情况交给人。[使用说明](https://docs.typesafe.ai/introduction)

TypeSafe 强调的也是这个方向：让模型更快地完成范围明确的判断，输出固定类型的结果，方便嵌进软件流程里。[官方定位](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

对我来说，这种形态值得关注。一个自动化流程里，经常需要做很多小判断：接下来走哪条分支，这一步有没有异常，要不要继续。这些判断如果能被程序直接接住，整个 workflow 就更容易串起来。

## 这给 AI Automation Testing 带来了一个新思路

一个能操作 App、把过程记录下来。另一个能根据给定的信息做分类和评分。

把这两种能力放到一起，就让我想到最近一直在折腾的 Verification Layer。

AI 把代码写出来，已经越来越容易了。但代码写完以后，谁来确认它真的满足了需求？这个问题，我觉得还远没有解决。

上一篇聊到，我们尝试用 Maestro 把测试执行稳定下来，但高质量 YAML 的编写和维护又成了新的成本。

现在，我想尝试另一种分工：把“怎么操作 App”和“结果是否符合预期”分开处理。

**能不能让 Artemis 去跑测试、留下 evidence，再让 Jev 对照验收标准做判断？**

这可能给 AI Automation Testing 多提供一条路：用自然语言驱动执行，再把实际结果交给专门的判断环节。

但这条路能不能走通，关键还在后半段。

## 跑完了，不代表测明白了

拿“取消订单”来说。

打开订单页，点击取消，确认，看到“取消成功”。自动化工具顺利跑完，给出一个 pass。

看起来没问题。

但如果后台的订单状态根本没变呢？如果接口明明失败了，App 却照样弹出了成功提示呢？

这时候，操作确实完成了，需求却没有被满足。

这也是我一直在意的地方：我们很容易把“流程跑通了”当成“功能做对了”。特别是 AI 自己跑测试、自己总结的时候，一句“验证通过”会把中间很多没检查的东西都盖过去。

所以我想把这两件事拆开：执行负责把实际情况带回来，验收负责对照事先确定的标准检查结果。

这样，AI 说自己完成了任务以后，后面还有东西能反驳它。

## Artemis 去跑，Jev 来看证据

回到刚才的订单例子，假设验收标准是：取消以后，页面和后台都要显示订单已取消。

Artemis 去完成操作，把页面上的内容记录下来。测试系统再通过额外接入的接口，拿到后台订单状态。

页面上的提示可以交给 Jev，判断它表达的是取消成功、取消失败，还是信息不够。后台状态是不是 `cancelled`，直接用程序检查就行。

如果页面说成功，后台却没变，这条 case 就不能过。模型对页面判断得再有把握，也改变不了后台状态这个事实。

这里还有个很现实的限制：**Jev 目前不能直接看截图。** 它接受的是文本形式的输入，也可以用结构化数据组织。因此，中间还需要把界面文字、操作记录和日志整理出来；只有截图的地方，则需要额外做识别。原始记录也得留着，判断错了才有地方回查。[输入说明](https://docs.typesafe.ai/concepts/state)

所以我脑子里的链路大概是这样：

> 先定验收标准 → Artemis 跑测试 → 整理 evidence → 程序检查 + Jev 判断 → 汇总结果 → 反馈给 Coding Agent

这几步，还是需要自己搭起来。

## 那不还是在用 AI 验证 AI？

是，这个担心完全合理。

如果只是让 Artemis 说一句“我做完了”，然后 Jev 说一句“我同意”，那两个模型完全可能一起判断错。

把执行和判断拆开，并不会自动让结果可靠。真正有用的，是让判断始终受验收标准和实际证据约束。

后台状态、错误码这些能直接检查的东西，就直接检查。需要理解页面含义的地方，再让 Jev 参与。证据没有拿到，就承认还判断不了。

我觉得测试结果至少应该有三种：**通过、失败、无法判断。**

比如，页面看起来正常，但查不到后台状态，那就是证据不够。手机断连了、操作根本没做完，也应该先归到执行问题，别直接告诉 Coding Agent“你的代码有 bug”。

这一点很重要。反馈给错了，agent 就会沿着错误的方向继续改。

置信度也是一样。

Jev 返回的 confidence，能帮助我们判断哪些结果需要再看一眼。但这个数来自它的概率分布，不等于“测试通过的概率”，更不保证它判断正确。[置信度说明](https://docs.typesafe.ai/confidence)

我不会因为一个分数很高，就把缺失的证据当成已经有了。一个模型非常确定，也可能只是非常确定地看错了。

## 先看看它能不能抓到 bug

所以，下一步我更想做一个小实验。

挑几个熟悉的 Android 场景，准备一份正常版本，再准备几份故意放进 bug 的版本。比如取消后状态不更新、请求失败却显示成功，或者漏掉一段关键证据。

然后让这套流程去跑，看看它能不能把这些情况分开。

我最关心的是：已经知道有 bug 的 case，它会不会依然很自信地判成通过？同一个 case 多跑几次，结论会不会变来变去？那些判不明白的情况，最后还要花多少人工去收拾？

如果测的是中文 App，还得单独看看中文效果。Jev 官方文档目前也提示，中文等语言的准确率低于英语。[语言限制](https://docs.typesafe.ai/concepts/state)

这些都需要实测。工具火不火，替代不了这一步。

如果它能稳定抓住问题，还能省下编写脚本、整理结果和人工复核的总时间，那这条路就值得继续。如果最后只是少写了一些 YAML，却多出一堆需要人判断的结果，那成本可能只是换了个地方。

到这里，这仍然是一个想法，还谈不上已经验证可行。但它让我觉得，Verification Layer 又多了一个可以动手试试的方向。

我想要的反馈其实很具体：哪条需求没有满足，实际发生了什么，证据在哪里，接下来该修代码还是补一次检查。

有了这些，Coding Agent 的下一轮修改才有依据。

Artemis 和 Jev 能不能一起把这件事做好，我想先拿几个真实的 case 跑一跑。能把一个本来会漏掉的 bug 稳定抓出来，就值得往下做。
